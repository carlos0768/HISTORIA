**Q1 の補足**: KC は「弱点として記録する知識の単位」であり、
「ウマイヤ朝とアッバース朝の区別」のような粒度で切る（`02-domain-model.md` §1）。
これを最初に何件作るかという判断だった。

- 800〜900件 = 世界史探究＋歴史総合の全範囲を覆う。作成に **12人日**
- **400件** = 共通テスト頻出に絞る。作成に **6人日**

400件を選ぶ理由は、**全部作ってから使い始めるより、狭くても早く回して測る方が学べる**ためである。
KC は**追加しても既存データを壊さない**（`kc` への INSERT であり、
`response` も `kc_card` も影響を受けない）ので、この判断は後から覆せる。

「未決」ではなく「**決めないことを決めた**」もの。

| 項目 | 理由 |

| SLA・稼働率目標 | 個人開発・非公開のため定めない（`12` §5） |
| 論述・記述式の AI 採点 | 対象試験が共通テスト＋私大マークであり出題されない。**実装しないと決めた**（`01` §4.3） |
| 他ユーザーとの比較・ランキング | 母集団が成立しない（`01` §4.3） |

| 多言語対応 | 日本の受験生のみが対象（`12` §9） |
| **1日の学習の「時間予算」** | **導入しない**（Q9・下記） |

### 5.1 時間予算を導入しないこと（Q9）

設計監査は「1日のノルマが問数単位で、教材の読解時間が計算に入っていない」ことを
blocker として挙げた。予測された帰結は次の2つである。

1. ホームに「42問」と出ても所要時間が分からず着手できない
2. 教材と出題が同じ日に競合したときどちらを削る規則が無く、キューが雪だるま式に積み上がる

**作者の決定は「導入しない」。** ノルマは問数のままにする。
時間予算を入れると `app_user` に1日の分数を持たせ、item を形式別の想定秒数で、
教材を文字数から見積もって分単位でノルマを組み直すことになり、
`05-scheduler.md` の中核（§3 の締切逆算と §4 のキュー構成）を作り直す規模になる。
**利用者が自分＋友人数人の段階で、その作り直しに見合う根拠がまだ無い。**

代わりに、既にある歯止めを明示しておく。

| 歯止め | 内容 |
|---|---|
| **上限が可変** | `app_user.max_daily_items`（10〜300）を本人と管理画面の両方から変更できる（Q6・`05` §9.1）。「多すぎる」と感じたら利用者自身が下げられる |
| **必ず打ち切る** | 出題キューは常に `MAX_DAILY` 件で打ち切る（`05` §4.2）。積み上がっても1日の提示量は上限を超えない |
| **達成不能を黙らせない** | `required > MAX_DAILY` のとき警告と選択肢（締切延長・範囲削減・続行）を出す（`05` §3.2） |

**再検討の引き金**を Phase 0 に置く。`13-roadmap.md` 手順 0-7 の2週間で
「毎日ノルマを終えているのに新しい範囲に進まない」が起きたら、この決定を見直す。
そのために実所要時間を記録する（M25）。
