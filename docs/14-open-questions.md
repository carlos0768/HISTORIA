### 1.-2 本番の Supabase を読んで見つけた RLS の穴（2026-09-02・修正済み）

作者がマイグレーションを流したので、初めて**本物のデータベース**に対して RLS を確かめられた。
仕様どおりに動いていなかったものが3件出た。いずれも手元の 343 件の試験は通っていた。

**なぜすり抜けたか。** 素の PostgreSQL と Supabase で既定が逆だからである。

| | 素の PostgreSQL | Supabase |
|---|---|---|
| `public` に作った表 | GRANT しない限り誰も触れない | `anon` / `authenticated` に **ALL が自動で付く** |
| RLS を掛け忘れた表 | 誰も読めない（安全側に倒れる） | **誰でも読み書きできる**（危険側に倒れる） |

本番で実測した値:

```sql
SELECT has_table_privilege('anon', 'public.kc', 'DELETE');  -- → true
```

つまり公開される anon キー1本で `kc` を全消しできる状態だった。

#### 見つかった3件

| # | 何が起きていたか | 直し方 |
|---|---|---|
| 1 | `v_weakness_evidence` が**定義者の権限で実行するビュー**だった（PostgreSQL の既定）。`response` の RLS を素通りするため、anon キーで `/rest/v1/v_weakness_evidence` を叩くだけで**全利用者の解答履歴**（誰が・どの KC を・何と答えて・正誤）が読めた | `WITH (security_invoker = true)` を明示 |
| 2 | **19 の表で RLS が無効**だった。`kc` / `syllabus_unit` / `invite_code` / `past_exam` などが含まれる。招待コードが読めれば招待制（上限10名）が崩れ、過去問の本文が読めれば `10` §2 の判断（非公開・招待制が前提）が崩れる | 42 表すべてで RLS を有効にし、読ませたい10表にだけ `FOR SELECT TO authenticated USING (true)` を書く |
| 3 | ポリシーが **PUBLIC 向け**だった。`material_select` の「`OR user_id IS NULL`」（共有教材）は anon にも当たるため、未ログインで共有教材の本文が読めた | 34 本すべてに `TO authenticated` を付ける |

#### 見つけ方と、繰り返さないための手当て

- `scripts/db/verify-rls.ts` を 22 → **52 項目**に増やした。追加したのは
  「マスタに**書き込めない**こと」「**anon** に何も見えないこと」「ビュー越しに他人の解答が漏れないこと」
- 検査そのものにも欠陥が2つあった。**どちらも「落ちるべき試験が通っていた」型**である
  - `response` の INSERT 試験が、存在しない列名を使っていた。RLS ではなく列エラーで失敗しており、
    RLS を外しても通ってしまう。実在する列に直し、**拒否の理由が RLS であること**まで見るようにした
  - `anon` の試験が、直前に `SET LOCAL` した JWT の claim を消していなかった。
    claim はトランザクション全体に残るので、anon なのに利用者Aの行が見えていた
- `scripts/db/schema.ts` に `SUPABASE_ROLES_SHIM` を足し、**手元と CI でも Supabase と同じ既定権限**を作る。
  ここを再現しない限り、同じ種類の穴はまた試験をすり抜ける（M30）
- `scripts/db/dump-rls.test.ts` が、表を1つ足して RLS を書き忘れたら落ちる

修正前 **45 / 52** → 修正後 **52 / 52**。

#### 本番への適用と、本物の `auth.uid()` での確認（2026-09-02・M22 決着）

（`ai_budget` / `ai_spend` / `app_setting` / `channel_allowlist` / `invite_code` /
`item` / `item_kc` / `kc_merge` / `kc_proposal` / `past_exam` ×3）。

`extension_in_public`（WARN・`vector` が public にある）は直していない。
移設は既存の型参照を全て書き換える作業になる一方、実害は拡張の関数が見える程度で、
上の3件とは危険度が2桁違う。意図して後回しにしている。

### 5.1 時間予算を導入しないこと（Q9）

設計監査は「1日のノルマが問数単位で、教材の読解時間が計算に入っていない」ことを
blocker として挙げた。予測された帰結は次の2つである。

1. ホームに「42問」と出ても所要時間が分からず着手できない
2. 教材と出題が同じ日に競合したときどちらを削る規則が無く、キューが雪だるま式に積み上がる

**作者の決定は「導入しない」。** ノルマは問数のままにする。
時間予算を入れると `app_user` に1日の分数を持たせ、item を形式別の想定秒数で、
教材を文字数から見積もって分単位でノルマを組み直すことになり、
`05-scheduler.md` の中核（§3 の締切逆算と §4 のキュー構成）を作り直す規模になる。
**利用者が自分＋友人数人の段階で、その作り直しに見合う根拠がまだ無い。**

代わりに、既にある歯止めを明示しておく。

| 歯止め | 内容 |
|---|---|
| **上限が可変** | `app_user.max_daily_items`（10〜300）を本人と管理画面の両方から変更できる（Q6・`05` §9.1）。「多すぎる」と感じたら利用者自身が下げられる |
| **必ず打ち切る** | 出題キューは常に `MAX_DAILY` 件で打ち切る（`05` §4.2）。積み上がっても1日の提示量は上限を超えない |
| **達成不能を黙らせない** | `required > MAX_DAILY` のとき警告と選択肢（締切延長・範囲削減・続行）を出す（`05` §3.2） |

**再検討の引き金**を Phase 0 に置く。`13-roadmap.md` 手順 0-7 の2週間で
「毎日ノルマを終えているのに新しい範囲に進まない」が起きたら、この決定を見直す。
そのために実所要時間を記録する（M25）。

### 5.2 16歳未満を受け付けないこと・生年月日を検証しないこと（作者判断・2026-09-02）

`10-legal-risk.md` §5.3 は当初「16歳未満は保護者のメールで同意を取る」と定めていた。
**作者の判断で「16歳未満は受け付けない」に変えた。** 理由と代償は §5.3 に書いた。

ここに残すのは、その決定に**残っているリスク**である。**実測で潰せる種類のものではない**
ので §2（着工前に実測すること）には置かない。

| 残存リスク | 内容 |
|---|---|
| **生年月日は自己申告** | 検証する手段が無い。16歳未満が16歳以上と偽って登録することは技術的に止められない。`lib/auth/age.ts` にできるのは「申告どおりなら断る」までである |
| **偽った登録を検知できない** | 招待制（上限10名・作者が直接コードを渡す）なので、**招待した相手が誰かは作者が知っている**。技術ではなく運用で担保している、というのが実態である |
| **施行日が未確定** | §5.1 のこども規律は政令待ちで施行日が確定していない（`10` §5.1 の要検証）。16歳未満を入れないという決定は、その不確定に実装を賭けない側に倒れている |

**この決定を見直す引き金**: 高1（15〜16歳）の友人を招待したくなったとき。
そのときは `10` §5.3 の旧仕様（保護者同意）に戻す。`app_user` の
`guardian_consent_required` / `guardian_email` / `guardian_consent_at` を
**そのために残してある**（列を消す費用は全員からの再同意である）。
