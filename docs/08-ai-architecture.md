# 08. AI アーキテクチャ・原価・品質保証

> 対象: HISTORIA MVP / 状態: 確定（v0.3 で全面改訂） / 最終更新: 2026-09-01
>
> **v0.2 からの変更**: 共有カタログ方式を廃止し、教材と設問をユーザーごとに生成する方針に変更した。
> **モデルは二層構成とする。生成は Gemini API の無料枠、検証は課金モデル**（§2）。
> 変更の理由は作者の指示であり、以下はその前提で最良を設計したものである。

## 0. v0.1 の矛盾の解消

v0.1 は「AIプロバイダー：GCP／使用モデル：Claude,ChatGPT」と書いていた。
**GCP Vertex AI に OpenAI の GPT 系商用 API は無い**ため、この2つは両立しない。

作者の指示（予算を Google の無料枠に収める）を踏まえ、次のように確定する。

## 1. 決定: Gemini API の無料枠を使う

### 1.1 「GCP の無料枠」で LLM が使えるのはどこか

**これは間違えやすい。** Google の生成AIには課金経路が2系統ある。

| 経路 | 無料枠 | 備考 |
|---|---|---|
| **Gemini API（AI Studio 系 / `generativelanguage.googleapis.com`）** | **あり（無期限・カード不要）** | 本プロジェクトが使うのはこれ |
| Vertex AI（`aiplatform.googleapis.com`） | **なし** | 生成モデルは常時課金。Claude on Vertex は Anthropic と同レート |
| GCP $300 無料トライアルクレジット | 新規アカウント90日限定 | 恒久的な「無料枠」ではない |

**決定: 生成に Gemini API の無料枠（Flash 系）を使う。Vertex AI は経由しない。**
**検証（ファクトチェックの二次照合・judge・診断プールの生成）には課金モデルを使う**（§2.1）。

### 1.2 無料枠の実態（2026年時点・**要検証**）

| 項目 | 値 |
|---|---|
| RPM（1分あたりリクエスト数） | **15** |
| RPD（1日あたりリクエスト数） | **1,500** |
| TPM（1分あたりトークン数） | **1,000,000** |
| 対象モデル | **Flash 系のみ**。Pro は2026年4月に無料枠から除外され有料のみ |
| クレジットカード | 不要 |
| 有効期限 | なし |
| **データの扱い** | **Google の製品改善（機械学習を含む）に使われる。人間のレビュアーが入力・出力に注釈を付けることがある**（§4） |

正確な数値とモデルIDは実装時に公式ドキュメントで確認すること（**要検証**）。
TPD（1日あたりトークン数）の上限があるかも確認が必要である（§3.3）。

### 1.3 この選択が持ち込む3つのリスク

| # | リスク | 対処 |
|---|---|---|
| R1 | **無料枠は予告なく変わる。** Pro が2026年4月に外された実績がある | プロバイダ抽象層を1枚置き、差し替え可能にする（§6） |
| R2 | **データが製品改善に使われる。** 未成年の成績プロファイルを扱う本アプリでは重大 | プロンプトから個人識別情報を完全に除去する（§4） |
| R3 | **Flash 系は事実精度が上位モデルより劣る可能性がある。** かつ毎回生成のため人手レビューが不可能 | 正典マスタとの機械照合を厚くし（§5 層2）、**検証だけ別系統の課金モデルに払う**（§2.1） |

## 2. モデル配置（二層構成）

**重い生成は無料枠で回し、安いが効く検証だけに金を払う。**

| 用途 | モデル | 課金 | 頻度 | 出力規模 |
|---|---|---|---|---|
| **教材＋設問の生成** | Gemini Flash 系 | **無料枠** | 1ユニット1回 | 12,000トークン |
| 範囲の自然文解釈 | Gemini Flash 系 | **無料枠** | 特訓作成時 | 数百トークン |
| **ファクトチェックの二次照合** | **Claude Sonnet 5** | **課金** | 1ユニット1回 | 400トークン |
| **診断プール240問の生成** | **Claude Sonnet 5** | **課金** | 一度きり | 185,000トークン |
| **LLM-as-judge（開発時のみ）** | **Claude Sonnet 5** | **課金** | プロンプト改善時 | 600トークン |
| 弱点判定 | **LLM を使わない** | — | — | SQL（`04-weakness-engine.md` §7） |
| 確認テストの採点 | **LLM を使わない** | — | — | DB内で完結 |

### 2.1 なぜ検証にだけ払うのか

v0.3 の当初案（全部無料枠）には**構造的な弱点**があった。

> 無料枠で使えるのは Flash 系のみで別系統のモデルを選べないため、
> 「別モデルによる採点」は実現できない。同一モデルである以上、同じ誤りを見逃す可能性は残る。

**この制約が、月あたり数百円で外れる。**

| 論点 | 内容 |
|---|---|
| **単価が2桁違う** | 生成は出力12,000トークン。検証は入力1,200・出力400トークン。**検証は生成の約1/20のコスト** |
| **訓練系統が変わる** | Google と Anthropic では学習データも手法も違う。**Flash が犯した誤りを見逃しにくい** |
| **人手レビューの代替になる** | 毎回生成では人手レビューが不可能（§5）。機械照合と別系統モデルが唯一の防衛線である |

**「品質に金を払う」なら、生成ではなく検証に払う方が費用対効果が高い。**
生成の品質を上げても誤りはゼロにならないが、検証を別系統にすると**見逃しの相関が下がる**。

### 2.2 検証モデルの選定

**Claude Sonnet 5（$2 / $10 per MTok）で確定**（作者の判断）。

検証は「この記述は史実として正しいか」を判定するだけの単純な作業であり、
より安価な Haiku 系でも足りる可能性はあった。**それでも Sonnet 5 を選ぶ。**

理由: **検証は人手レビューの唯一の代替である**（§5）。毎回生成では作者が教材を読めず、
誤りを止められるのは層2の機械照合と層3のこのモデルだけになる。
月額の差は数百円であり、**ここで安さを取ると製品の前提が崩れる**。

月額は 5人×1特訓で約144円、10人×3特訓で約864円（§3.4）。予算1万円に対して9%であり、
数分の1に削る動機がない。

### 2.3 送信先が2社になることの帰結

生成は Google、検証は Anthropic へ送る。プライバシー上はむしろ改善する。

| | 送信先 | 送る内容 | 学習に使われるか |
|---|---|---|---|
| 生成 | Google（無料枠） | KC の id・3段階の習得度・単元id | **使われる**（§4 の匿名化で対処） |
| 検証 | Anthropic（課金） | **本文から抽出した歴史的主張のテキストのみ** | 使われない（有料枠） |

**検証プロンプトには KC の id すら不要である。**「ウェストファリア条約は1648年に締結された」
という歴史的主張の文字列だけを送る。**個人に紐づく情報はゼロ**であり、
匿名化の必要すらない。プライバシーポリシーには両社を明記する（`10-legal-risk.md` §8b.2）。

## 3. リクエスト数の試算

コストではなく **RPD / RPM の消費**が制約になる。

### 3.1 1ユニットあたりのリクエスト数

```
教材＋設問の生成      1 リクエスト
ファクトチェック照合   1 リクエスト（照合できない claims がある場合のみ）
─────────────────────
合計                  2 リクエスト
```

### 3.2 1日あたりの消費

| 想定 | ユニット/日 | リクエスト/日 | RPD 1,500 に対して |
|---|---|---|---|
| 5人 × 1特訓 × 1ユニット/日 | 5 | 10 | **0.7%** |
| 10人 × 3特訓並行 | 30 | 60 | **4.0%** |
| 10人 × 3特訓 ＋ 初回の一括生成（1人10ユニット） | 130 | 260 | **17.3%** |

**無料枠の RPD には十分な余裕がある。** 上限に近づくのは、
10人が同時期に特訓を新規作成して大量の先読み生成が走る場合だけである。

### 3.3 トークンの試算

| 項目 | トークン |
|---|---|
| 出力（本文3,500字＋FC12枚＋四択8問＋claims 20件） | 12,168 |
| 入力（システム＋候補KC 30件＋単元＋弱点情報） | 2,700 |
| **1ユニット合計** | **14,868** |

- 10人 × 3特訓 = 30ユニット/日 → **約 446,000 トークン/日**
- バースト時でも生成は1ユニット110〜180秒かかるため、TPM 1,000,000 には届かない

**要検証**: 無料枠に TPD（1日あたりトークン数）の上限があるか。
あるなら 446,000 トークン/日 が収まるかを実装前に確認する。

### 3.4 課金する部分の原価

生成は無料枠なので0円。課金するのは検証系だけである
（Claude Sonnet 5 = $2 / $10 per MTok・1USD=150円）。

| 項目 | 入力 / 出力 | 単価 | 想定量 | 月額 |
|---|---|---|---|---|
| ファクトチェックの二次照合 | 1,200 / 400 | **0.96円** | 5人×1特訓（150ユニット/月） | **約144円** |
| 同上 | | | 10人×3特訓（900ユニット/月） | **約864円** |
| LLM-as-judge（開発時のみ） | 12,000 / 600 | 4.50円 | A/Bテスト1回＝40件 | 約180円/回 |
| 診断プール240問 | 15,000 / 184,800 | — | 一度きり | **約282円** |

**予算1万円に対して、想定の重い側でも 900円弱（9%）。**

初期費用は診断プールの約282円のみ。以後の月額は利用者数と特訓数に比例するが、
**検証は入出力が小さいため、ユーザーが10倍になっても1万円には届かない**
（100人×3特訓で約8,600円/月）。

### 3.5 無料枠が使えなくなった場合の原価（退避計画）

R1 に備え、有料に落ちた場合の金額を算出しておく。

| 退避先 | 1ユニット | 10人 × 3特訓 × 30日（900ユニット） |
|---|---|---|
| Gemini 有料（Flash 系） | 約 2〜4円（**要検証**） | 1,800〜3,600円/月 |
| Claude Sonnet 5（$2/$10 per MTok・1USD=150円） | 約 18.9円 | **17,010円/月** ← 予算超過 |
| Claude Sonnet 5 ＋ 非同期バッチ（約50%割引） | 約 9.5円 | 8,550円/月 |

**この判断は今は行わない（作者の決定）。** 無料枠の条件変更が実際に起きた時点で、
下記を見て決める。Phase 0 では検討しない。

**生成まで Claude に退避すると予算 1万円を超える。** そのときは
(a) 利用者を5人に絞る (b) 教材の文字数を減らす (c) 共有カタログ方式に戻す
のいずれかが必要になる。

**なお (c) が最も安い。** 共有カタログなら400ユニット × 18.9円 = **7,560円の一度きり**
（非同期バッチで50%引きなら3,780円）で以後ほぼ0円になり、**さらに人手レビューもできる**。
「毎回生成 × 上位モデル」は3つの選択肢のなかで最も高くつく組み合わせであり、
品質に金を払うなら共有カタログに戻す方が安全である。この判断は
`14-open-questions.md` Q4 に未決として記録する。

## 4. 無料枠のデータ利用への対処（最重要）

**無料枠に送ったデータは Google の製品改善（機械学習を含む）に使われ、
人間のレビュアーが入力・出力に注釈を付けることがある。**
Google 自身が非有料サービスに機密・個人情報を送らないよう案内している。

HISTORIA は **16歳未満を含む未成年の成績プロファイル**を扱う（`10-legal-risk.md` §5）。
このまま個人の学習データを送るのは、同意を取ったとしても筋が悪い。

### 4.1 決定: プロンプトから個人識別情報を完全に除去する

教材生成に必要なのは「**どの KC が弱いか**」であって「**誰が**」ではない。

```
送ってよいもの:
  - syllabus_unit.id（'wh.2.4.1'）      … 公開されている教科書の章立て
  - kc.id のリスト（'kc.islam.umayyad_vs_abbasid'）… 本アプリが定義した公開語彙
  - 各KCの習得度の帯（'low' / 'mid' / 'high'）      … 数値ではなく3段階に丸める
  - 反復して選ばれた誤選択肢のラベル（'アッバース朝'）… 歴史用語であって個人情報ではない

送ってはいけないもの:
  - user_id / 表示名 / メールアドレス / 生年月日
  - 生の正答率・解答時刻・解答履歴
  - 連続学習日数・累計解答数などの行動ログ
  - 自由入力欄の内容（範囲指定の自然文を除く）
```

送信内容は「**イスラーム史のこの3項目が弱い学習者向けに教材を書け**」という形になり、
特定の個人に紐づかない。

### 4.2 実装で強制する

```
lib/ai/redact.ts
  export function buildGenerationContext(userId): AnonymizedContext

  戻り値の型に user_id / email / birth_date を含めない（型で防ぐ）。
  この関数を通さないコンテキストを LLM クライアントに渡せないようにする
  （クライアントの引数型を AnonymizedContext に限定する）。
```

`AnonymizedContext` を通らない経路を作らないこと。これに対するテストを書き、
個人識別情報がプロンプトに混入しないことを固定する。

### 4.3 プライバシーポリシーに明記する

> **学習内容の生成のため**、あなたが苦手としている単元・項目の識別子を Google（Gemini API）へ送信します。
> 氏名・メールアドレス・生年月日・解答履歴そのものは送信しません。
> 無料枠を利用しているため、送信された内容は Google のサービス改善に利用される場合があります。
>
> **生成された文章の事実確認のため**、教材から抽出した歴史的な記述（「◯◯条約は△△年に締結された」等）を
> Anthropic へ送信します。この送信にあなたに関する情報は一切含まれません。
> 有料の枠を利用しているため、送信された内容がモデルの学習に使われることはありません。

**この一文を書けない設計にしない。** 書けるように §4.1 を守る。

## 5. ハルシネーション対策 — 5層（毎回生成に合わせて再設計）

世界史は年号・人名・因果が命であり、**受験生は誤りを検知できない読者**である。

v0.2 では共有カタログ400件を人手レビューする前提だったが、
**毎回生成では人手レビューが物理的に不可能になる**（生成量がレビュー容量を無限に超える）。
さらに Flash 系は上位モデルより事実精度が劣る可能性がある。

**したがって機械照合が唯一の防衛線になる。ここを厚くする以外に手はない。**

### 層1: 生成時に主張を構造化出力させる

`07-content-pipeline.md` §5.3 の `claims` 配列。本文と同時に
「本文中の検証可能な主張（年号・人物・出来事・因果・地名）」を strict JSON で吐かせる。

### 層2: 正典マスタとの機械照合（**この層の重要度が跳ね上がった**）

```sql
CREATE TABLE canon_event (
  id         text PRIMARY KEY,
  label      text NOT NULL,
  aliases    text[] NOT NULL DEFAULT '{}',
  year_from  int NOT NULL,
  year_to     int,
  precision  text NOT NULL CHECK (precision IN ('exact','decade','century')),
  region_ids smallint[] NOT NULL DEFAULT '{}'
);
```

```
kind='year' の claim について:
  claim.subject を canon_event.label / aliases と照合
  → 年が食い違えば FLAG
  → 照合できなかったら層3へ
kind='person' の claim は person テーブルと照合
```

**正典マスタの規模を v0.2 の 1,500件から 3,000件に増やす。**
人手レビューが無くなった分をここで埋める。作成工数は 2人日 → **4人日**。

照合率の目標: **教材中の `kind='year'` と `kind='person'` の claim の 80% 以上が機械照合できること。**
Phase 0 で実測し、下回るならマスタを追加する（`13-roadmap.md`）。

### 層3: **別系統の課金モデル**による二次照合

層2で照合できなかった claim だけを、**生成に使ったのとは別系統のモデル**へ、
**生成時のコンテキストを渡さずに**問い直す。

```
生成: Gemini Flash 系（無料枠）
検証: Claude Sonnet 5（課金）        ← 訓練系統が違う

入力: 「次の記述は史実として正しいか。前後の文脈は与えない」＋ claim のリスト（1,200トークン）
出力: 各 claim に { verdict: 'correct'|'incorrect'|'uncertain', reason }（400トークン）
単価: 0.96円/ユニット
```

**これが人手レビューの喪失に対する主たる代替手段である。**
同一モデルの自己検証では同じ誤りを見逃すが、Google と Anthropic では
学習データも手法も違うため**見逃しの相関が下がる**。

`incorrect` が1件でも出たら層5へ。`uncertain` が3件以上でも同様。

### 層4: ユーザー報告導線（**毎回生成では最後の砦**）

全教材ページ・全問題に「この記述はおかしい」ボタンを置く。

```sql
CREATE TABLE content_report (
  id          bigserial PRIMARY KEY,
  user_id     uuid NOT NULL,
  target_kind text NOT NULL CHECK (target_kind IN ('material_section','item')),
  target_id   uuid NOT NULL,
  comment     text,
  status      text NOT NULL DEFAULT 'open'
              CHECK (status IN ('open','confirmed','dismissed','fixed')),
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

報告が付いた段落は**即座に非表示**にし、再生成キューへ入れる。

毎回生成では同じ誤りが他のユーザーに出るとは限らないため、
**報告は個別の教材の修正にしかならない**。共有カタログなら1件の修正が全員に効いたが、その利点は失われた。
代わりに、報告された claim を `canon_event` に追加する運用にして層2を育てる。

### 層5: 事実確認を通らなかった教材は**配信しない**（作者の決定）

**方針: 誤りが検出されたらエラーにして、その教材ユニットを出さない。**

v0.3 の当初案は「FLAG された段落だけを落として残りを表示する」だったが、
作者の判断でこれを強化した。**部分的に落とした教材は、抜けたまま読まれる。**
受験生は何が省略されたか分からず、因果の連鎖が途切れた文章を読むことになる。

```
生成
  ↓
層2（canon_event 照合）＋ 層3（別系統モデルによる二次照合）
  ↓
FLAG なし        → status = 'ready'      配信する
FLAG あり        → 該当セクションを再生成（自動・最大2回）
  ↓
再生成後も FLAG  → status = 'blocked'    ★ 配信しない
                   blocked_reason に検出内容を記録（作者が見る）
                   ユーザーには「この単元の教材は作れませんでした」
                   → 自学モードに降格し、設問だけを出す（§5.1）
```

FLAG の条件:

| 条件 | 判定 |
|---|---|
| 層3で `incorrect` が **1件以上** | 再生成 → 残れば `blocked` |
| 層3で `uncertain` が **3件以上** | 同上 |
| 層2で年号・人名の不一致が **1件以上** | 同上 |

### 5.1 配信できなかったときのユーザー体験

**教材が出なくても学習は止めない。**

```
「この単元の教材は作れませんでした。教科書で学習してください。」
  ＋ [ 問題演習だけ始める ]   ← 設問は別途評価されるので出せる
  ＋ [ もう一度作ってみる ]   ← 手動での再試行（1日1回まで）
```

設問（`item`）は教材とは独立に評価する。**設問は1問単位で落とせる**ため、
誤りが検出された設問だけを `hidden = true` にし、残りは出題する。
ある KC の設問が全滅した場合は `pick_item()` が `null` を返し、
その KC はその日の出題からスキップされる（`04b-spaced-repetition.md` §5）。

### 5.3 設問（item）の承認経路

**教材は「配信するか / しないか」の二値だが、設問は1問単位で落とせる。**
`item.approved = true` になって初めて出題される。false のままの設問は
`pick_item()` の候補に入らない（`04b-spaced-repetition.md` §5）。

| 種別 | 承認する主体 | `approved_by` | タイミング |
|---|---|---|---|
| **ユーザー生成の設問**（`user_id` 非NULL） | **ファクトチェックのパイプライン（自動）** | `'factcheck'` | 層2・層3 を通過した時点でサーバーが `true` にする |
| **診断プール**（`user_id IS NULL`） | **作者（手動）** | `'author'` | 240問を全件レビューして `true` にする |

```
教材の生成が完了
  ↓
層2（canon_event 照合）＋ 層3（別系統モデルによる二次照合）
  ↓
その設問に紐づく claim に FLAG なし
  → item.approved = true / approved_by = 'factcheck' / approved_at = now()
  ↓
FLAG あり
  → approved = false のまま、hidden = true / hidden_reason = 'factcheck_flag'
     その設問は出題されない。同じ KC の他の設問は出題される
```

**毎回生成では人手レビューが不可能なため、`approved` は自動でしか立たない。**
これは `approved` の意味が v0.2（作者が読んで承認した）から
v0.3（機械検証を通過した）に変わったということである。
`approved_by` を必ず残すのは、後から「どちらの経路で通ったか」を区別するためである。

ある KC の設問が全て `approved = false` になった場合、`pick_item()` は `null` を返し、
その KC はその日の出題からスキップされる。**設問が全滅した KC は
`generation_job(kind='items_refresh')` をキューに入れて作り直す。**

### 5.2 この決定が意味すること

**誤りの混入を「品質問題」から「可用性問題」に変換している。**

| | 当初案（部分省略） | 決定（配信しない） |
|---|---|---|
| 誤りが受験生に届くか | 届きうる（省略されなかった誤りは残る） | **届かない** |
| 誤り率が高いとどうなるか | 品質の低い教材が配られる | **教材が出ない頻度が上がる** |
| 検知できるか | しにくい（誰も気づかない） | **すぐ分かる**（`blocked` の件数を数えるだけ） |

したがって **Phase 0 の判定基準も変わる**（`13-roadmap.md`）。

```
旧: 「20ユニットで事実誤りが3件以下」
新: 「20ユニットのうち配信できるユニットが 17本（85%）以上」
```

誤り率が高くても誤情報は配られない。代わりに「教材が出ない」という形で現れるので、
**その頻度が許容できるかどうかで判断する**。

## 6. プロバイダ抽象層（二層構成の実装と R1 への備え）

無料枠は予告なく変わる。**モデル呼び出しを1箇所に閉じ込める。**

**v0.3 では2プロバイダの併用が常態である**（生成=Gemini / 検証=Anthropic）。
抽象層はもともと退避のために置いたが、日常的に両方を使う。

```
lib/ai/
  client.ts        -- generate(ctx: AnonymizedContext, schema): Promise<T>
                   -- verify(claims: Claim[]): Promise<Verdict[]>
  providers/
    gemini.ts      -- 生成用。Gemini API 無料枠
    anthropic.ts   -- 検証用。課金。生成への退避先も兼ねる
  redact.ts        -- AnonymizedContext を組み立てる唯一の入口（§4.2）
```

```
GEN_PROVIDER    = 'gemini'     | 'anthropic'   -- 生成。既定 gemini
GEN_MODEL       = モデルID
VERIFY_PROVIDER = 'anthropic'  | 'gemini'      -- 検証。既定 anthropic
VERIFY_MODEL    = モデルID
```

**生成と検証は必ず別プロバイダにする。** 両方が同じ値になる設定を起動時に拒否する
（同一モデルの自己検証に退化するため）。退避で生成を Anthropic に移すときは、
検証を Gemini 側に入れ替えて別系統を保つ。

**アプリのどこからも `fetch` で直接 LLM を呼ばない。** `client.ts` だけが外に出る。
これにより、無料枠が消えた日に env を1つ変えるだけで退避できる。

## 7. レート制限とリトライ

無料枠は 15 RPM である。**同時実行を絞る。**

| ガード | 実装 |
|---|---|
| 同時生成数 | アプリ全体で **3並列まで**（`generation_job` の `status='running'` を数える） |
| RPM 超過（429） | 指数バックオフ（2s / 4s / 8s）・**最大3回**。SDK の自動リトライは無効化して一元管理する |
| RPD 超過 | その日の生成を停止し、UI に「本日の生成上限に達しました」を出す。**学習機能は止めない**（§8） |
| 冪等キー | `generation_job (user_id, kind, scope_id, params_hash)` に UNIQUE 制約。リロード連打で二重生成しない |
| ユーザー単位の上限 | 1日 **10ユニット**まで。同時 active な特訓は **5本**まで |
| 検証側（Anthropic）の支出上限 | コンソールで **月 3,000円で通知 / 5,000円で停止**。想定は900円弱なので、超えたらバグを疑う |

```sql
CREATE TABLE generation_job (
  id            uuid PRIMARY KEY,
  user_id       uuid REFERENCES app_user(id) ON DELETE CASCADE,
  kind          text NOT NULL
                CHECK (kind IN ('material','factcheck','scope_parse')),
  scope_id      text NOT NULL,
  params_hash   text NOT NULL,
  status        text NOT NULL DEFAULT 'queued'
                CHECK (status IN ('queued','running','succeeded','failed','cancelled')),
  attempts      smallint NOT NULL DEFAULT 0,
  provider      text NOT NULL,
  model         text NOT NULL,
  input_tokens  int, output_tokens int,
  error         text,
  created_at    timestamptz NOT NULL DEFAULT now(),
  started_at    timestamptz, finished_at timestamptz,
  UNIQUE (user_id, kind, scope_id, params_hash)
);
CREATE INDEX ON generation_job (status, created_at) WHERE status IN ('queued','running');
```

## 8. 実行基盤 — 先読み生成が必須になった

### 8.1 v0.2 からの後退

v0.2 では共有カタログを作者がオフラインで作る設計だったため、
**ユーザー起点の長時間生成が存在せず、ジョブ基盤そのものが不要だった**。

毎回生成にしたことで、この利点は失われる。1ユニットの生成は
出力12,000トークン超で **110〜180秒**かかり、Vercel Functions の上限
（Hobby 標準60秒 / Fluid Compute 300秒）に対して危険である。
途中で切れた生成は**課金だけ発生して成果物が残らない**（無料枠では RPD だけ消費する）。

### 8.2 決定: 先読み生成 ＋ ジョブテーブル ＋ ポーリング

**ユーザーを待たせないために、次に読む分を前もって作っておく。**

```
特訓を作成した時点          → 最初の1ユニットを即座にキューへ（この1回だけは待たせる）
ユーザーがアプリを開いた時点 → 「明日以降に読む予定の未生成ユニット」を最大2件キューへ
教材を読み終えた時点        → 次のユニットが未生成ならキューへ
```

締切逆算で「明日何を学ぶか」は決まっている（`05-scheduler.md`）ため、先読みできる。

```
POST /api/materials/generate  → generation_job に enqueue して 202 を返す
GET  /api/materials/:jobId    → status を返す（クライアントは3秒間隔でポーリング）
ワーカー                       → Vercel Function（Fluid Compute・maxDuration 300）で1ジョブ処理
```

**1ジョブ＝1ユニット**にする。複数まとめると300秒を超える。

### 8.3 初回の待ち時間

特訓作成直後の1本目だけは 110〜180秒待たせることになる。UI で正直に見せる
（`11-ux.md` の生成待ち状態）。

```
「教材を作っています（およそ2〜3分）」
＋ 進捗の段階表示（本文 → 設問 → 事実確認）
＋ 「できたら通知する」を選べるようにし、画面を離れられるようにする
```

### 8.4 Cron の使い道

Vercel Cron は Hobby で1日1回、**失敗しても UI に出ない**。学習機能を載せない。

| 用途 | Cron に載せるか |
|---|---|
| 1日1通の学習リマインド | ○ |
| YouTube の週次生存確認 | ○ |
| **先読み生成** | **✗**。ユーザーのアクセスを契機にする（§8.2） |
| ノルマの再計算 | ✗。ログイン時の遅延評価（`05-scheduler.md` §7） |

## 9. 未成年ユーザーとモデル提供元の規約

想定ユーザーはほぼ全員が未成年である。世界史は戦争・虐殺・宗教対立・植民地支配を扱うため、
**未成年向けの安全フィルタと衝突して生成が拒否される事故が起きうる**。

システムプロンプトに教育目的である旨を明記する（`07-content-pipeline.md` §5.1）。

**着工前に、次の10単元でプロンプト検証を行う（要検証）。**

```
十字軍 / アヘン戦争 / 三角貿易と奴隷制 / ナチス・ドイツとホロコースト /
インド大反乱 / アルメニア人問題 / 南京事件を含む日中戦争 / 太平洋戦争と原爆 /
アパルトヘイト / 文化大革命
```

**毎回生成では、拒否が起きたユーザーはその場で教材を得られない。**
共有カタログなら作者が事前に検知して人手執筆に切り替えられたが、その退路はない。
拒否された場合は「この単元の教材を生成できませんでした。教科書で学習してください」と出し、
`mode='self_study'` 相当に降格させる（設問だけは別プロンプトで再試行する）。
