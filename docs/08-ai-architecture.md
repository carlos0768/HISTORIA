# 08. AI アーキテクチャ・原価・品質保証

> 対象: HISTORIA MVP / 状態: 確定 / 最終更新: 2026-09-01

## 0. v0.1 の矛盾の解消

v0.1 は次のように書いていた。

```
・AIプロバイダー：GCP
・使用モデル：Claude,ChatGPT
```

**これは技術的に両立しない。** GCP Vertex AI / Model Garden で提供されるのは Claude（Anthropic）と
OpenAI のオープンウェイトモデル（gpt-oss 系）であり、**ChatGPT すなわち OpenAI の GPT 系商用 API は
GCP からは呼べない**。さらに、2モデルを併用する理由（用途分け）も書かれていなかった。

これを放置すると最初のコード行が書けない。SDK・認証方式・課金先・レート制限の単位・エラー型・
ストリーミングのイベント形式がすべて変わるためである。

## 1. 決定: Anthropic 直 API に1本化する

| 項目 | 決定 |
|---|---|
| プロバイダ | **Anthropic 直 API**（`@anthropic-ai/sdk`） |
| GCP Vertex 経由 | **使わない** |
| OpenAI 併用 | **しない** |

Vertex 経由を採用しない理由:

- Vertex の Claude は Anthropic 標準レートだが、**リージョナル／マルチリージョンのエンドポイントでは
  標準比10%のプレミアム**がかかる
- プロンプトキャッシュの扱いが本家 API と非対等で、**コスト最適化の手段が本家より狭い**
- 認証が GCP ADC / サービスアカウント鍵になり、Vercel の環境変数管理が複雑になる
- 個人開発で GCP を挟む積極的な理由がない（GCP クレジットを消化したい等の事情がない限り）

安価モデルの併用は **ファクトチェックの二次照合と教材の採点にのみ**行う（§5、§6）。
これは「2モデル併用」ではなく「用途が明確に分かれた2階層」である。

## 2. モデル配置

| 用途 | モデル | 呼び出し方 | 理由 |
|---|---|---|---|
| 教材本文＋item の生成 | **Claude Sonnet 5** | Message Batches API | 品質とコストの均衡。教材はこの製品の中核 |
| 教材の採点（LLM-as-judge） | **安価モデル**（Claude Haiku 系） | Batches API | 採点はルーブリックが明確で、高性能モデルを要さない |
| ファクトチェックの二次照合 | **安価モデル** | Batches API | 生成に使ったモデルとは別系統にする（同じ誤りを見逃さないため） |
| 個人差分の生成 | **Claude Sonnet 5** | 同期 | 短く（400字）、即時性が要る |
| 範囲の自然文解釈（`07` §8.2） | **Claude Sonnet 5** | 同期 | 構造化出力・数百トークン |
| 弱点判定 | **LLM を使わない** | SQL | `04-weakness-engine.md` §7 |

**採点とファクトチェックは生成に使ったモデルと別のモデルで行う。**
自己採点は甘くなり、同じモデルは同じ誤りを見逃す。

※ 安価モデルの正確な料金は実装時に **要検証**。本文書の原価試算は安全側に倒し、
すべて Sonnet 5 の料金（$2 / $10 per MTok）で計算している。

## 3. 原価試算

前提: 1 USD = 150 円 / Claude Sonnet 5 = 入力 $2 / 出力 $10 per MTok /
**日本語 1文字 ≈ 1.2 トークン**（※この換算は `count_tokens` での実測が必須。**要検証**）

### 3.1 教材ユニット1本の生成コスト

| 出力物 | 文字数 | トークン |
|---|---|---|
| 本文（`07` §2 の7セクション） | 3,500 | 4,200 |
| フラッシュカード 12枚（約60字/枚） | 720 | 864 |
| 四択 8問（設問＋4選択肢＋誤答解説4本＋正答解説、約640字/問） | 5,120 | 6,144 |
| `claims` 20件（約40字/件） | 800 | 960 |
| **出力合計** | **10,140** | **12,168** |

| 入力 | トークン |
|---|---|
| システムプロンプト | 800 |
| 候補KC 30件 | 1,080 |
| 単元コンテキスト | 320 |
| **入力合計** | **2,200** |

```
同期（通常レート）: 12,168 × $10/1M + 2,200 × $2/1M = $0.1261 ≈ 18.9 円
Batches API（約50%割引）:                                        ≈  9.5 円
自学モード（本文なし・item のみ）:                                ≈  5.5 円
```

### 3.2 共有カタログの一括構築（一度きり）

対象は `syllabus_unit` の節レベル約400件（世界史探究 約300／歴史総合 約100）。

| 工程 | 単価 | 件数 | 小計 |
|---|---|---|---|
| 教材＋item の生成（Batch） | 9.5円 | 400 | 3,800円 |
| LLM-as-judge による採点（Batch） | 2.4円 | 400 | 960円 |
| ファクトチェック二次照合（Batch） | 0.5円 | 400 | 200円 |
| 基準未達の再生成（20%が1回と仮定） | 11.9円 | 80 | 952円 |
| **合計** | | | **約 5,900円（一度きり）** |

以後の**限界費用はほぼゼロ**である。ユーザーが1人増えても100人増えても、
この 5,900円 は増えない。これが共有カタログ方式を採る最大の理由である。

### 3.3 月額のランニングコスト

| 項目 | 単価 | 想定量 | 月額 |
|---|---|---|---|
| 個人差分の生成 | 1.0円/回 | 1人が月30ユニット閲覧 | 30円/人 |
| 範囲の自然文解釈 | 0.3円/回 | 1人が月5回 | 1.5円/人 |
| 確認テストの採点 | **0円** | DB内で完結 | 0円 |
| 診断テスト | **0円** | カタログ済み item を出すだけ | 0円 |
| YouTube API | **0円** | 無料枠内（`09b-video.md` §4） | 0円 |
| **AI 合計** | | **5人** | **約 160円/月** |

| インフラ | プラン | 月額 |
|---|---|---|
| Vercel | Hobby（非商用・個人利用） | 0円 |
| Supabase | Free | 0円 |
| **想定合計** | | **約 160円/月** |

**予算上限 1万円に対して十分な余裕がある。**
Supabase Free は一定期間の非アクティブでプロジェクトが一時停止される制約があるため
（**要検証**）、実運用で問題が出れば Pro（約3,750円/月）に上げても合計 3,900円/月で収まる。

### 3.4 前提が崩れた場合

| 前提が崩れる条件 | 影響 | 対処 |
|---|---|---|
| 一般公開してユーザーが100人になる | 個人差分が 3,000円/月 | クォータ（§4）で頭打ちにする。カタログ本体は影響なし |
| 個人ごと生成に方針転換する | 400円/人月 → 5人で2,000円、100人で40,000円 | **転換しない**。`07` §3.2 |
| 教材を Opus 系で生成する | カタログ構築が約3倍 | 品質差をベンチマーク（`07` §6）で測ってから判断する |

## 4. コスト暴走の防止

v0.1 には上限・クォータ・認証・リトライの記述が一切なかった。

| ガード | 実装 |
|---|---|
| **冪等キー** | `generation_job(user_id, scope_id, params_hash)` に UNIQUE 制約。リロード連打で5回課金されるのを防ぐ |
| **ユーザー月次クォータ** | `users.monthly_token_budget`（既定 200,000 出力トークン ≈ 300円）。超過時は生成を停止し UI に残量を出す |
| **同時特訓数の上限** | 1ユーザーあたり **5本**（v0.1 は「同時に複数」としか書いておらず、50本作られると原価が50倍になる） |
| **リトライ** | 指数バックオフ・**最大3回**。Anthropic SDK は既定 `max_retries=2` で 408/409/429/5xx を自動リトライするため、**アプリ側で重ねると実効試行回数が乗算される**。SDK 側を `max_retries: 0` にしてアプリ側で一元管理する |
| **認証必須** | 生成系エンドポイントは全て認証必須。無認証で叩ける生成APIは、URLが割れた時点で第三者にトークンを焼かれる |
| **組織レベルの支出上限** | Anthropic コンソールで支出アラートを設定する（アプリ側のバグを最後に止める防波堤） |

```sql
CREATE TABLE generation_job (
  id           uuid PRIMARY KEY,
  user_id      uuid,                         -- カタログ構築時は NULL
  kind         text NOT NULL CHECK (kind IN ('material','personalization','scope_parse','judge','factcheck')),
  scope_id     text NOT NULL,                -- syllabus_unit.id など
  params_hash  text NOT NULL,
  status       text NOT NULL DEFAULT 'queued'
               CHECK (status IN ('queued','running','succeeded','failed','cancelled')),
  attempts     smallint NOT NULL DEFAULT 0,
  batch_id     text,                         -- Anthropic Message Batches の ID
  input_tokens int, output_tokens int, cost_jpy real,
  error        text,
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  UNIQUE (user_id, kind, scope_id, params_hash)
);
```

## 5. ハルシネーション対策 — 4層

世界史は年号・人名・因果が命であり、**受験生は誤りを検知できない読者**である。
誤った教材で暗記したら模試で失点する。1件の誤りがサービスの信頼を壊す。

v0.1 のこだわり方は「**プロンプトを色々試す**」だけで、検証パイプラインが存在しなかった。

### 層1: 生成時に主張を構造化出力させる

`07-content-pipeline.md` §5.3 の `claims` 配列。本文と同時に
「本文中の検証可能な主張（年号・人物・出来事・因果・地名）」を strict JSON で吐かせる。
本文を再度 LLM に読ませる必要がなくなる。

### 層2: 正典マスタとの機械照合

```sql
CREATE TABLE canon_event (
  id         text PRIMARY KEY,
  label      text NOT NULL,
  aliases    text[] NOT NULL DEFAULT '{}',
  year_from  int NOT NULL,
  year_to    int,
  precision  text NOT NULL CHECK (precision IN ('exact','decade','century')),
  region_ids smallint[] NOT NULL DEFAULT '{}'
);
```

```
kind='year' の claim について:
  claim.subject を canon_event.label / aliases と照合
  → 一致した場合、claim.year_from が canon_event の範囲と食い違えば FLAG
  → 照合できなかった場合は層3へ回す
kind='person' の claim も person テーブルと同様に照合する
```

正典マスタは KC のシードと同時に作る（`02-domain-model.md` §8）。
**約1,500件の年号・人物を持てば、教材中の主張の過半を機械照合できる**（**要検証**）。

### 層3: 別モデルによる二次ファクトチェック

層2で照合できなかった claim だけを、**生成に使ったのとは別のモデル**にまとめて渡す。

```
入力: 単元名 + 照合できなかった claim（通常5〜10件）
出力: 各 claim に対し { verdict: 'correct'|'incorrect'|'uncertain', reason: string }
```

`incorrect` が1件でも出たら `material.status = 'flagged'` にして人手レビューキューへ。
`uncertain` が3件以上でも同様。

### 層4: ユーザー報告導線

全教材ページ・全問題に「**この記述はおかしい**」ボタンを置く。

```sql
CREATE TABLE content_report (
  id          bigserial PRIMARY KEY,
  user_id     uuid NOT NULL,
  target_kind text NOT NULL CHECK (target_kind IN ('material_section','item')),
  target_id   uuid NOT NULL,
  comment     text,
  status      text NOT NULL DEFAULT 'open'
              CHECK (status IN ('open','confirmed','dismissed','fixed')),
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

報告が付いた**段落は即座に非表示**にし（`material_section.hidden = true`）、再生成キューへ入れる。
「報告を受け付けたが表示は続ける」は、誤情報を配布し続けることと同じである。

**共有カタログ方式だからこの4層が回る。** 人手レビューの対象は400件で有限であり、
1件の修正が全ユーザーに効く。個人ごと毎回生成では、層4はともかく層3の人手レビューが
物理的に不可能になる（生成量がレビュー容量を無限に超える）。

### 着工前の実測

**代表20単元を生成し、年号・人名の誤りを人手で数える。**
混入率が分かって初めて、層2の正典マスタをどこまで作るべきかが決まる。
この実測なしに「4層あるから大丈夫」とは言えない。

## 6. 実行基盤 — MVP では長時間ジョブ基盤を持たない

### 6.1 Vercel の制約

| 項目 | 値 |
|---|---|
| Function `maxDuration` | Hobby 標準 **60秒** / Fluid Compute 有効時 **300秒** / Pro も上限 300秒 |
| Cron | Hobby は **1日1回**、実行時刻は指定時間内の任意 |

3,500字＋item の生成は出力12,000トークン超であり、生成に **110〜180秒** かかる。
Hobby の60秒では完走しない。ストリーミングにしてもクライアントに逐次届くだけで、
**関数の実行時間上限は消えない**。途中で切れた生成は**課金だけ発生して成果物が残らない**。

### 6.2 決定: ユーザー起点の長時間生成を MVP に作らない

これが本仕様で最も効く設計判断である。

```
カタログ構築（400ユニット・110〜180秒/件）
  → 作者がローカル / CI から実行する オフラインスクリプト ＋ Anthropic Message Batches API
  → Vercel を一切経由しない。実行時間の制約が消える

ユーザー起点の LLM 呼び出し
  → 個人差分（出力480トークン・1〜3秒）と 範囲の自然文解釈（数百トークン・1〜2秒）のみ
  → 同期リクエストで完結する
```

**MVP では、ユーザーが特訓を作れる範囲を「カタログ生成済みの `syllabus_unit`」に限定する。**
カタログは作者が事前に全400ユニット分を作っておくため、この制約は実質的に何も制限しない
（範囲は世界史探究＋歴史総合の全体を覆う）。

結果として MVP では次がすべて不要になる。

- ジョブキュー基盤（QStash / Inngest / Trigger.dev）の選定と外部依存
- ポーリング／SSE による進捗通知
- 中断した生成のリカバリ
- Vercel Cron の頻度制約との戦い

`generation_job` テーブル（§4）はカタログ構築スクリプトが使う。Vercel 上では動かさない。

### 6.3 Phase2 で必要になったら

ユーザーが任意の範囲を自由記述して即座に教材を作る機能を足すときに、初めてジョブ基盤が要る。
そのときは **Anthropic Message Batches API ＋ `generation_job` テーブルのポーリング**を第一候補とする
（外部サービスを増やさずに済み、50%割引も効く）。締切まで日数がある集中特訓の性質と、
「数分〜数時間で結果が返ればよい」という Batches の特性は合致する。

### 6.4 Cron の使い道

Vercel Cron は Hobby で1日1回しか回せず、**失敗しても UI に出ない**。
したがって**学習機能をここに載せない**。

| 用途 | Cron に載せるか |
|---|---|
| 1日1通の学習リマインド通知 | ○ |
| YouTube の週次生存確認（`09b-video.md` §4.2） | ○（週1回で足りる） |
| ノルマの再計算 | **✗**。ログイン時の遅延評価にする（`05-scheduler.md` §7） |
| SM-2 の due 判定 | **✗**。クエリ時に `due_at <= now()` で引くだけ |

## 7. 未成年ユーザーとモデル提供元の規約

想定ユーザーは高校生であり、ほぼ全員が未成年である。

- Anthropic は、未成年にサービスを提供する組織に対して**年齢確認・コンテンツモデレーション・
  監視体制・児童プライバシー法の遵守・提供される子ども向けシステムプロンプトの実装**を求めている
- これは「あったらいい」ではなく**規約上の提供条件**である。違反によるアカウント停止は
  個人開発者にとって即死を意味する（予備の契約先がない）

### 7.1 世界史アプリ固有のリスク

**世界史は戦争・虐殺・宗教対立・植民地支配を扱う。** ホロコースト・十字軍・アヘン戦争・
奴隷貿易の記述が未成年向けの安全フィルタと衝突し、生成が拒否される事故が起きうる。

対策として、システムプロンプトに教育目的である旨を明記する
（`07-content-pipeline.md` §5.1 の6番目の項目）。

**着工前に、次の10単元でプロンプト検証を行う（要検証）。**

```
十字軍 / アヘン戦争 / 三角貿易と奴隷制 / ナチス・ドイツとホロコースト /
インド大反乱 / アルメニア人問題 / 南京事件を含む日中戦争 / 太平洋戦争と原爆 /
アパルトヘイト / 文化大革命
```

拒否や過度な婉曲が起きた単元は、システムプロンプトの調整か、当該単元のみ人手執筆に切り替える。

## 8. 実装前に検証すること

1. `count_tokens` で日本語1文字あたりのトークン数を実測する（**原価試算の全前提**）
2. 代表20単元を生成し、年号・人名の誤り件数を人手で数える（§5）
3. §7.1 の10単元でモデルの拒否・婉曲が起きないかを確認する
4. Message Batches API の実際の割引率と所要時間を1バッチで測る
5. 安価モデル（Haiku 系）の現行料金を確認し、判定・照合の単価を確定する
6. Vercel Hobby の非商用利用条項が本アプリ（非公開・招待制・無償）に適合するか確認する
