# 12. 非機能要件

> 対象: HISTORIA MVP / 状態: 確定 / 最終更新: 2026-09-01

## 1. 性能目標

| 操作 | 目標 | 根拠 |
|---|---|---|
| ホーム表示 | p95 < 800ms | `daily_plan()` の遅延評価を含む。`O(active drill の KC 数)` = 数百件 |
| 出題の取得（次の1問） | p95 < 300ms | `card (user_id, due_at) WHERE NOT suspended` のインデックス1本で引く |
| 解答の記録 | p95 < 400ms | `response` INSERT ＋ `user_kc_state` / `card` の同期更新（`O(item の KC 数)` = 1〜3） |
| 教材セクションの表示 | p95 < 500ms | 共有カタログから読むだけ |
| 個人差分の生成 | p95 < 4s | LLM 同期呼び出し（出力480トークン）。**初回のみ。以後キャッシュ** |
| 確認テストの採点 | p95 < 600ms | DB 内で完結（LLM を使わない） |
| 診断テストの次問選択 | p95 < 500ms | 12セルの事後分布の更新のみ |

**LLM 呼び出しがユーザーの待ち時間に乗るのは「個人差分」と「範囲の自然文解釈」の2箇所だけである**
（`08-ai-architecture.md` §6.2）。それ以外はすべて DB で完結する。

## 2. コスト上限とガード

| 層 | ガード | 値 |
|---|---|---|
| ユーザー単位 | `app_user.monthly_token_budget` | 200,000 出力トークン（約300円）／月 |
| ユーザー単位 | 同時 active な特訓数 | **5本** |
| リクエスト単位 | 冪等キー `generation_job (user_id, kind, scope_id, params_hash)` | UNIQUE 制約 |
| アプリ単位 | リトライ | 指数バックオフ・最大3回。SDK 側は `max_retries: 0` にして一元管理 |
| 組織単位 | Anthropic コンソールの支出アラート | 月 3,000円で通知、10,000円で停止 |
| インフラ | Vercel / Supabase の使用量アラート | 各プランの上限の80%で通知 |

**月額の目標は 1,000円未満**（試算は約160円。`08-ai-architecture.md` §3.3）。
**絶対上限は 10,000円**であり、超える見込みが立った時点で生成を止める。

### 2.1 予算超過時の挙動

```
monthly_token_budget を使い切った場合:
  ・既存の教材の閲覧、フラッシュカード、四択、確認テストは通常どおり動く
  ・個人差分の生成のみ停止し、共有カタログの本文だけを表示する
  ・「今月の生成上限に達しました。来月1日にリセットされます」を控えめに表示する
```

**学習を止めない。** 課金が止まっても閉ループの中核（測定と出題）は DB だけで回る設計になっている。

## 3. Vercel の制約と対応

| 制約 | 値 | 対応 |
|---|---|---|
| Function `maxDuration` | Hobby 標準60秒 / Fluid Compute 300秒 / Pro も上限300秒 | ユーザー起点の長時間生成を作らない（`08` §6.2）。カタログ構築はオフラインスクリプト |
| Cron | Hobby は1日1回・実行時刻は指定時間内の任意 | 学習機能を cron に載せない。リマインド通知と動画の週次確認のみ |
| Cron の失敗が UI に出ない | ― | ノルマ再計算を cron でやらない（遅延評価にする） |
| 非商用利用条項（Hobby） | ― | 本アプリは非公開・招待制・無償なので該当すると考えられるが **要検証** |

## 4. Supabase の制約と対応

| 制約 | 対応 |
|---|---|
| Free プランは一定期間の非アクティブでプロジェクトが一時停止される（**要検証**） | 数人での利用では実際に起きうる。問題が出れば Pro（約3,750円/月）に上げる |
| Serverless からの直接接続はコネクションを食い潰す | **Supavisor（transaction モード）経由で接続する** |
| Free プランのストレージ・帯域上限 | 教材は最大でも 400 × 4KB = 1.6MB。画像を保存しない設計なので問題にならない |

## 5. 可用性・データ保全

| 項目 | 方針 |
|---|---|
| SLA | 定めない（個人開発・非公開） |
| **バックアップ** | `response` が唯一の真実（`03-data-model.md` §2.2）。**週1回、`response` / `app_user` / マスタ系を pg_dump して外部ストレージに保存する**。他の全テーブルはここから再生成できる |
| マスタの管理 | KC・教材・item は CSV / JSON で git 管理する（`09-content-sourcing.md` §7）。DB を唯一の真実にしない |
| 障害時の復旧 | 新しい Supabase プロジェクトを作り、`schema.sql` → seed → `response` のリストア → 再計算 |

**`response` さえ守れば学習履歴は失われない。** これが導出テーブル設計の副次効果である。

## 6. セキュリティ

| 項目 | 方針 |
|---|---|
| 認証 | Supabase Auth ＋ Google ログイン。招待コード必須 |
| 認可 | **RLS を全ユーザーデータテーブルで有効化**（`schema.sql` §13）。API 層のバグでも他人のデータが漏れない |
| `response` の不変性 | RLS で SELECT / INSERT のポリシーのみ作り、UPDATE / DELETE を作らない |
| APIキー | サーバー側の環境変数のみ。`NEXT_PUBLIC_` プレフィックスを付けない。クライアントから LLM を直接呼ばない |
| 生成系エンドポイント | **全て認証必須**。無認証で叩けると URL が割れた時点で第三者にトークンを焼かれる |
| CSP | `frame-src https://www.youtube-nocookie.com` / `img-src 'self' data: https://i.ytimg.com` |
| `robots.txt` | 全面 `Disallow` ＋ `noindex`（`10-legal-risk.md` §3.2 G3） |
| 依存関係 | Dependabot を有効化。`npm audit` を CI で実行 |

## 7. 監視

個人開発なので**最小構成**にする。ただし「静かに壊れる」ものだけは必ず検知する。

| 対象 | 方法 | なぜ必要か |
|---|---|---|
| **アプリのエラー** | Sentry の無料枠 | |
| **LLM 呼び出し** | `generation_job` に `input_tokens` / `output_tokens` / `cost_jpy` を記録し、日次の合計を「記録」タブの管理者ビューに出す | コストの暴走を早期に見つける |
| **cron の実行結果** | 実行のたびに `ops_log` に記録し、**24時間記録がなければ次のログイン時に作者へ警告を出す** | cron の失敗は UI に出ないため、能動的に検知する必要がある |
| **動画の生存** | 週次バッチの結果（`unavailable` になった件数）を記録 | 再生できない動画が放置されるのを防ぐ |
| **誤り報告** | `content_report (status='open')` の件数をホームに出す（作者のみ） | 誤情報の放置がこの製品で最も重い障害 |

LLM の可観測性ツール（Langfuse 等）は MVP では導入しない。
`generation_job` テーブルで足りる規模である。
