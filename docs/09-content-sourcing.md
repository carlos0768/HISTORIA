# 09. コンテンツ調達計画

> 対象: HISTORIA / 状態: 確定 / 最終更新: 2026-09-01

## 0. この文書が解く問題

v0.1 は5つの機能を並べていたが、**「そのコンテンツはどこから来るのか」に一切答えていなかった**。

- タイムラインの「出来事」は誰が作るのか
- Wiki の「重要な単語」の一覧はどこにあるのか
- 過去問はどこから取ってくるのか
- 確認テストの問題は誰が作るのか

**0件のDBではアプリは何も表示しない。** ローンチ時に何件必要かを数値で決める。

## 1. ローンチ時に必要なデータ量

| データ | 件数 | 作り方 | 担当 | 人日 |
|---|---|---|---|---|
| `syllabus_unit`（部・章・節） | **約80** | 教科書の目次を手入力 | 作者 | 1 |
| `era` / `region` / `region.grid_id` | 3 / 約30 | 手入力 | 作者 | 0.5 |
| `kc` | **800〜900** | AI が章ごとに提案 → 作者が1件ずつ承認 | 作者＋AI | **12** |
| `person` | 約400 | KC 作成時に併せて登録 | 作者＋AI | （上記に含む） |
| `canon_event`（正典マスタ） | **約1,500** | 年号・人物の正解値。KC 作成時に併せて | 作者＋AI | 2 |
| `material`（教材） | **400ユニット** | Batches API で生成 → judge → 人手レビュー | AI＋作者 | **10** |
| `item`（設問） | **約8,000** | 教材と同一生成パスで自動生成（1ユニット20問） | AI | （上記に含む） |
| `channel_allowlist` | 10〜15 | 作者が手で選ぶ | 作者 | 0.5 |
| `video` | 2,000〜3,000（候補）→ 承認 800〜1,200 | `playlistItems.list` で吸い上げ → 埋め込みで KC 対応付け → 作者承認 | 作者＋API | 3 |
| **合計** | | | | **約29人日** |

**`item` が約8,000件になる**（400ユニット × 平均20問）。これがこの製品の実質的な資産である。
Anki で自分でカードを作る場合と比べたときの差別化が、ここに集約されている（`01-product.md` §2.3）。

## 2. KC シードの作成手順（クリティカルパス）

**全体工数78人日のうち12人日を占める最大の作業である。** ここを軽く見積もると計画が崩れる。

```
1. 教科書の目次を syllabus_unit に手入力（約80行）
2. 各節について、次のプロンプトで KC 候補を出させる:

   「{節名} で、受験生が間違えやすい『区別』『因果』『年代順』『地理比定』『事実』を
    10〜12件挙げてください。各項目に kind と、なぜ間違えやすいかを付けてください。
    用語の単純な暗記項目は挙げないでください（それは item で扱います）。」

3. 出力を kc_proposal に積む（80節 × 11件 ≒ 880件）
4. 作者が1件ずつ承認する。承認時に kind / era_id / kc_region / exam_weight を確定する
   → 1件あたり45秒として 880件 ≒ 11時間
5. 重複を pgvector の近傍検索で検出し（cosine 0.85 以上）、統合する
6. KC ラベルを埋め込み、kc.embedding に格納する
```

**この作業を AI に全自動でやらせない。** KC の粒度と重複がその後のすべて（弱点推定の統計、
教材の分割、item の対応付け）を決めるため、ここだけは人間が見る。
`02-domain-model.md` §5 の「LLM に KC を生成させない」は、運用時の話であると同時に、
シード作成時にも作者の承認を挟むという意味である。

## 3. タイムライン（Phase2）

MVP では実装しないが、**方針だけ確定しておく**（後から変更するとコストが跳ね上がるため）。

### 3.1 単一列にしない

v0.1 は「時代を指定するとその時代の出来事が Twitter のタイムラインのように流れてくる」としていた。

**単一列に全地域を混ぜると学習価値が出ない。** 17世紀の欄に清・ムガル・オスマン・
イングランド革命・三十年戦争が無秩序に混在し、地域の区別がつかない列になる。
これはタテ（通史）の可視化にもヨコ（同時代性）の把握にもならない。

受験世界史で得点差がつくのは**ヨコ**、すなわち「同じ時期に諸地域で何が並行して起きていたか」である。

**決定: 地域を列にした多レーン表示、または地域タグ＋地域別の色分けによる並置ビューにする。**
これは `timeline_event` に `region_id` が必須であることを意味する
（`02-domain-model.md` の `region` マスタが前提になる）。

### 3.2 事前生成する

| 方式 | コスト | 判定 |
|---|---|---|
| **オンデマンド生成** | 1画面50記事 × 6行 × 40字 ≒ 12,000字 ≒ 約20円。**スクロールのたびに発生** | **不可**。1人が10画面眺めるだけで200円。「サブ的な機能」の原価がメイン機能を上回る |
| **事前バッチ生成** | 時代20 × 地域6 = 120画面 × 50記事 = 6,000記事 ≒ 180万出力トークン ≒ **約2,700円の一度きり** | **採用**。以後は限界費用ゼロ・レイテンシゼロ・ファクトチェックも1回で完了 |

**これは本質的に有限集合である。** 世界史の出来事は無限にはない。全部作ってDBに置くのが正しい。

### 3.3 「6行」を文字数に置き換える

行数はデバイス幅で変わるため生成プロンプトの制御パラメータにならない。
**1記事 240字 ±15%** とする（v0.1 の「6行」をスマホ幅40字 × 6行として換算した値）。

### 3.4 出来事データの調達

| 案 | 評価 |
|---|---|
| **AI 生成（事前バッチ）** | **採用**。KC と同じ体系で作れる。ファクトチェックは `canon_event` との照合で回る |
| Wikidata SPARQL | 日本語ラベルの充足率と、受験世界史に必要な粒度との不一致が課題（**要検証**）。補助的に使う余地はある |
| 手作業 | 6,000記事は非現実的 |

## 4. Wiki 用語マスタ（Phase2）

### 4.1 MVP ではリンクを張らない

v0.1 は「重要な単語にはリンクを設定し Wikipedia に飛ばす」「世界史専用の学習用ページでもいい」
「**両方実装しておく**」としていた。

**MVP では教材にリンクを一切張らない**（`07-content-pipeline.md` §10）。理由は3点。

1. **「重要な単語」の判定基準が無い。** 山川『世界史用語集』のような頻度指標を使わないと、
   AI が「重要」と判断した語がユーザーの志望校レベルと無関係になる
2. **表記ゆれの正規化が無い。** 「フビライ／クビライ」「ムハンマド／マホメット」
   「ティムール朝／ティムール帝国」など受験世界史は表記が複数流通しており、
   AI 生成本文の語をそのまま Wikipedia 記事名に投げると**誤リンクが記事数に比例して蓄積し、
   後から手作業で直せない規模になる**
3. **飛んだ先が受験の到達範囲を意識していない。** 不要な情報を大量に読むことになり、
   再読問題（`07` §0）を悪化させる

### 4.2 Phase2 の設計

```sql
CREATE TABLE term (
  id          text PRIMARY KEY,          -- 'term.abbasid_caliphate'
  label       text NOT NULL,             -- 正規表記
  reading     text,                      -- 読み
  frequency   smallint,                  -- 教科書での掲載頻度（1〜7）
  level       text CHECK (level IN ('common_test','private_mark','advanced')),
  kc_id       text REFERENCES kc(id),
  wikipedia_title text,                  -- 曖昧性解消済みの記事名
  description text                       -- 自前の学習用説明（100〜200字）
);
CREATE TABLE term_alias (
  term_id text NOT NULL REFERENCES term(id) ON DELETE CASCADE,
  alias   text NOT NULL,
  PRIMARY KEY (term_id, alias)
);
```

- **リンクは `term` に登録された語のみに張る。** 未登録語にはリンクを張らない
- `wikipedia_title` は**手動で曖昧性解消を済ませた記事名**を保持する
  （「アレクサンドロス」「李世民」のような同名異人・別名を先に解決する）
- 語彙数の目標は 3,000〜5,000。山川『世界史用語集』の採録語数は約5,200語とされるが、
  共通テスト＋私大マークに必要な範囲に絞る（**要検証**）
- 「両方実装」のうち、**先に自前の学習用ページ（`term.description`）を作る**。
  Wikipedia へのリンクは補助リンクとして併置する

### 4.3 Wikipedia 本文を教材生成に使わない

CC BY-SA 4.0 の継承義務の問題（`10-legal-risk.md` §7）。
`term.description` も**自前で書く／AI に書かせる**のであって、Wikipedia から転記しない。

## 5. 過去問（Phase2）

法的な整理は `10-legal-risk.md` §3 にある。ここではデータ調達の観点のみ扱う。

### 5.1 入手可能なソース

| ソース | 入手性 | 注意 |
|---|---|---|
| 大学が自サイトで公開している PDF | 大学による。公開している大学は多い | 各大学の二次利用ポリシーを個別に確認する必要がある |
| 大学入試センターの公開問題 | 公開されている | **事前の「試験問題利用申請」が必要**とされる |
| 市販の問題集（赤本等） | 書籍 | データベース化の許諾は**一律で断られている** |

### 5.2 スクレイピングの可否判断

```
1. 対象サイトの robots.txt を確認し、Disallow されていれば取得しない
2. 利用規約に自動取得の禁止条項がないか確認する
3. 大学の二次利用ポリシーページを確認する
4. アクセス間隔を最低5秒空ける
5. 上記のいずれかで不可なら、その大学は諦める（無理をしない）
```

**個人開発で全大学を網羅する必要はない。**
MVP の次のステップとして **3〜5大学 × 3年分**から始める（約100設問）。

### 5.3 PDF/OCR の現実的難易度

世界史の設問構造は「リード文 → 下線部 → 設問群」であり、PDF のレイアウトも複雑である。

- テキスト埋め込み PDF なら抽出は容易だが、**設問の構造化（どの設問がどの下線部に対応するか）は難しい**
- スキャン PDF は OCR が必要で、旧字体・地図・系図の扱いが困難
- **Vision LLM でページ画像から構造化 JSON を出させる方が現実的**（**要検証**）

いずれにせよ `past_exam_element` の要素分解（`10-legal-risk.md` §3.3）に落とす必要があり、
**1設問あたり数分の人手確認が必要**である。100設問で数日かかる。

### 5.4 MVP での代替

**確認テストの設問は100%自作／AI生成である**（`10-legal-risk.md` §4.2）。
世界史は事実の問題であるため、現代文・英語と違って自作で十分な品質が出せる。

過去問が無くても閉ループ（`01-product.md` §3）は完全に成立する。
過去問の価値は「本番の形式への慣れ」と「傾向の把握」であり、**Phase2 で足せばよい**。

## 6. RAG は MVP では使わない

v0.1 は「AIが参照できる過去問データベース」を grounding のソースとして想定していたが、
**過去問は設問文であって、教材本文の事実根拠にはならない**。

さらに MVP では過去問自体が存在しない。

**決定: MVP で pgvector を使うのは次の2箇所のみ。RAG（検索して生成に渡す）は行わない。**

| 用途 | 埋め込む対象 |
|---|---|
| KC の候補絞り込み（LLM に「この中から選べ」と渡す） | `kc.label` |
| 動画と KC の対応付け | `video.title + description` |

教材の事実正確性は **RAG ではなく `canon_event` との機械照合**で担保する
（`08-ai-architecture.md` §5 層2）。これは決定的な照合であり、
ベクトル検索の曖昧さが入らない分、年号の検証には適している。

Phase2 で `term.description` や過去問が揃ったら、RAG の導入を再検討する。

## 7. seed スクリプトの設計

```
scripts/
  seed/
    01_masters.ts        -- era / region / person / syllabus_unit（CSV から投入）
    02_kc.ts             -- kc / kc_region / kc_syllabus_unit（承認済み CSV から投入）
    03_canon.ts          -- canon_event
    04_catalog.ts        -- 教材＋item の一括生成（Batches API）。冪等
    05_judge.ts          -- LLM-as-judge による採点
    06_factcheck.ts      -- canon_event 照合 ＋ 二次ファクトチェック
    07_video.ts          -- channel_allowlist から候補収集 → 埋め込み → 対応付け
  ops/
    video_healthcheck.ts -- 週次の生存確認（09b-video.md §4.2）
```

**すべて冪等にする。** `generation_job` の UNIQUE 制約（`08-ai-architecture.md` §4）により、
同じ `(kind, scope_id, params_hash)` の再実行は課金されない。
400ユニットの生成が途中で失敗しても、再実行すれば未完了分だけが走る。

**マスタは CSV で git 管理する。** DB を唯一の真実にしない。
KC の追加・修正の履歴が git に残り、レビューできる。
