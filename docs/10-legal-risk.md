## 1. 入試問題の著作権の構造

### 1.1 二層構造

入試問題の権利は2層になっている。

| 層 | 権利者 |
|---|---|
| 試験問題**全体**（編集著作物）／個々の**問題**（言語の著作物） | **実施主体**（大学・大学入試センター） |
| 問題文中に引用された**第三者著作物**（史料の翻訳文、研究者の文章、地図・図版・写真） | **各権利者** |

大学から問題全体の利用許諾を得ても、**第三者部分は別途各権利者から許諾を取る必要がある**
というのが権利処理実務の共通理解である。

### 1.2 実務がどうなっているか

- **大学入試センター**は、試験問題の二次利用に**事前の「試験問題利用申請」**を求めている
- **教学社（赤本）**は、入試問題の**データベース化については「教学社のみでは許諾を出せない」として
  一律で断っている**
- 赤本ですら第三者著作物の権利処理が完了せず、「**著作権の都合により省略**」の表示が恒常的に発生している
- 権利処理は人力での権利者探索を伴う大規模な作業である（大学側が専門部署に委託している例がある）

**世界史は英語・現代文より第三者著作物の比率が小さい**（主たる権利者は大学）が、ゼロではない。
数百字のリード文、史料の現代語訳・翻訳文（**翻訳は二次的著作物で翻訳者に権利が残る**）、
地図・系図・美術作品の写真が該当する。

## 2. よくある3つの誤解

### 誤解1: 「入試問題だから36条で無許諾でいける」

著作権法36条1項は「入学試験その他人の学識技能に関する試験又は検定の目的上必要と認められる限度」での
複製・公衆送信を認める。しかし裁判例上、その射程は
**試験の公正な実施（＝事前に問題を知られては困ること）に必要な場合に限られる**と解されており、
**市販教材や学習用コンテンツは対象外**とされる。加えて36条2項は、営利目的で複製・公衆送信する者に
通常の使用料相当額の**補償金の支払義務**を課す。

**アプリ内の反復可能な確認テストは「公正な実施」の要請が働かないため、36条には乗らない。**

> ※ 東京地判平成16年5月28日（国語教科書事件）に関する二次資料の解説に依拠。判決原文は **未確認**。

### 誤解2: 「AIに読ませるだけだから30条の4（情報解析）でいける」

30条の4は「著作物に表現された思想又は感情を**自ら享受し又は他人に享受させることを目的としない場合**」の規定である。

v0.1 の「AIが参照できる過去問データベース」は RAG（検索拡張生成）であり、
**出力としてユーザーに元の表現を見せることが目的に含まれる**。
文化庁の「AIと著作権に関する考え方について」（令和6年3月）でも、
学習データの創作的表現を直接感得できる生成物を出力することが目的と評価される場合は
**享受目的が併存し30条の4は適用されない**とされている。

RAG の出力側については47条の5（軽微利用）の可能性が示されているが、同条は
(a) 利用が付随的であること (b) 利用が「軽微」であること (c) 政令で定める基準に適合する者であること
を要件とする。**過去問1問を丸ごと提示する行為は「軽微利用」の枠に収まらない。**

### 誤解3: 「非営利・個人開発だから大丈夫」

38条の非営利無償の上演等に関する規定は、**複製権・公衆送信権には及ばない**。
非営利であることは、複製・送信の適法性の根拠にならない。

**ただし30条（私的使用のための複製）は別である。** これが本プロジェクトの実際の依拠点になる（§3）。

## 3. 過去問の扱い（Phase2）

### 3.1 30条の射程と、その境界

著作権法30条は「個人的に又は家庭内その他これに準ずる限られた範囲内において使用する」ための複製を認める。

- **作者が自分だけで使う**: 30条の範囲内と考えられる
- **友人数人に配信する**: 「家庭内その他これに準ずる限られた範囲」を**超える可能性がある**。
  この文言は通常「家族や、ごく親しい少数の友人」といった閉じた関係を指すと解されているが、
  サーバ上に複製物を置いて公衆送信する形態は、複製権に加えて**公衆送信権**の問題が別途生じる
  （「公衆」は不特定または特定多数を指し、特定少数への送信は公衆送信にあたらないと解されるが、
  「少数」の線引きは明確でない）

**したがって作者の決定（本文格納・友人数人へ提供）は、30条の内側とも外側とも断定できないグレーゾーンにある。**
作者はこれを承知の上で選択している。本文書はその前提で、**リスクを最小化する設計**を規定する。

### 3.2 リスク低減のための実装ガード（Phase2 で必須）

| # | ガード | 目的 |
|---|---|---|
| G1 | **招待制**。招待コードなしにアカウントを作れない | 「限られた範囲」を維持する |
| G2 | 過去問を含む全ページで**認証必須**。未認証は404を返す | 公衆送信性を下げる |
| G3 | `robots.txt` で全面 `Disallow`、`<meta name="robots" content="noindex,nofollow">` | 検索エンジンにインデックスされない |
| G4 | 過去問本文の**コピー・ダウンロード導線を置かない**（PDF出力・エクスポート機能を作らない） | 再頒布を防ぐ |
| G5 | 全過去問に**出典表示**（大学名・年度・学部）を必ず付ける | 出所の明示 |
| G6 | **削除申立ての窓口**（メールアドレス）をアプリ内とプライバシーポリシーに明記し、申立てから72時間以内に非表示化する運用を決めておく | 対応の遅れは損害の拡大要因になる |
| G7 | **利用者数の上限を設ける**（招待コードの発行上限 10名） | 「限られた範囲」の客観的な担保 |

### 3.3 データモデル: 要素分解を最初から入れる

**これは MVP の時点でスキーマに入れる。後から分解するのは不可能だからである。**

過去問レコードを1カラムに丸ごと入れると、「リード文だけ削除」「図版だけ差し替え」といった
部分マスキングが後からできず、**1箇所の権利問題で1問まるごと削除するしかなくなる**。
赤本ですら「著作権の都合により省略」が発生していることを踏まえれば、部分的に権利処理できない領域を
持つ構造は必須である。

```sql
CREATE TABLE past_exam (
  id           uuid PRIMARY KEY,
  university   text NOT NULL,
  faculty      text,
  year         smallint NOT NULL,
  sitting      text,                       -- '前期' '全学部日程' 等
  subject      text NOT NULL,
  source_url   text,                       -- 大学が公開している PDF の URL
  created_at   timestamptz NOT NULL DEFAULT now()
);

-- ★ 1問を要素に分解して持つ。要素ごとに権利状態を管理する。
CREATE TABLE past_exam_element (
  id            uuid PRIMARY KEY,
  exam_id       uuid NOT NULL REFERENCES past_exam(id) ON DELETE CASCADE,
  question_no   text NOT NULL,
  element_kind  text NOT NULL
                CHECK (element_kind IN ('stem','lead_text','source_material','figure','choices','answer')),
  ord           smallint NOT NULL,
  body          text,                      -- 本文。withheld のときは NULL
  rights_status text NOT NULL DEFAULT 'needs_permission'
                CHECK (rights_status IN ('self_made','public_domain','licensed','needs_permission','withheld')),
  rights_source text,                      -- 権利者・許諾の根拠・PD の理由
  withheld_note text,                      -- 「著作権の都合により省略」に相当する表示文言
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON past_exam_element (exam_id, question_no, ord);
CREATE INDEX ON past_exam_element (rights_status);

-- 過去問とKCの対応（メタデータ。事実であり著作物ではない）
CREATE TABLE past_exam_kc (
  exam_id     uuid NOT NULL REFERENCES past_exam(id) ON DELETE CASCADE,
  question_no text NOT NULL,
  kc_id       text NOT NULL REFERENCES kc(id),
  PRIMARY KEY (exam_id, question_no, kc_id)
);
```

**図版は自作の模式図か、パブリックドメイン（Wikimedia Commons の PD-old 等）に限定する。**

## 4. `CONTENT_MODE` スイッチ

**一般公開に切り替えた瞬間に、30条の依拠が完全に崩れる。**
この切り替えを「気をつける」で運用してはならない。**コードで強制する。**

```
CONTENT_MODE = 'private' | 'public'      -- 環境変数。既定は 'private'
```

| | `private` | `public` |
|---|---|---|
| `past_exam_element.body` の返却 | `rights_status ∈ (self_made, public_domain, licensed)` のみ返す。それ以外は本文を返さず、`withheld_note` と `source_url` を返す | **一切返さない**（`rights_status` を問わず） |
| 過去問の提示 | 本文＋出典 | **メタデータ＋大学公開PDFへのリンク＋AI生成類題**にフォールバック |
| 招待制 | 有効 | 任意 |
| 教材・item | 変更なし | 変更なし |

### 4.1 実装位置

**切り替えは API 層の1箇所で効くようにする。**

```
app/api/_lib/content-mode.ts
  export function redactExam(element, mode) { ... }

過去問を返すすべての経路（Route Handler / Server Action / RSC）は、
必ずこの関数を通してから返す。DB から直接クライアントに渡す経路を作らない。
```

この関数に対するテストを書き、`mode='public'` で `body` が絶対に漏れないことを固定する。

### 4.2 確認テストの設問は100%自作／AI生成に限定する

`CONTENT_MODE` にかかわらず、**確認テストに過去問本文を出さない**（§2 の誤解1）。

確認テストは弱点DBの唯一の入力源であり、ここが違法設計だと
弱点DB → ホーム → 次の集中特訓というループ全体が止まる。

**世界史は事実の問題であるため、現代文・英語と違って自作で十分な品質が出せる。**
これがこの製品にとっての救いである（`06-assessment.md`）。

過去問の使い道は Phase2 でも「**傾向の提示**」と「**類題の生成元（内部参照）**」に限定し、
本文をそのまま出題に使わない。

### 4.3 公開前チェックリスト

`CONTENT_MODE='public'` に切り替える前に、次をすべて満たすこと。

- [ ] `past_exam_element.body` を返す経路が全て `redactExam()` を通っていることをコードレビューで確認
- [ ] `mode='public'` で `body` が漏れないテストが通る
- [ ] AI生成類題へのフォールバックが全画面で動作する
- [ ] 利用規約・プライバシーポリシーを公開仕様に更新する
- [ ] 16歳未満の同意フロー（§5）が実装済み
- [ ] 削除申立て窓口が機能している
- [ ] AIプロバイダの未成年向け要件（§6）を満たしている
- [ ] 原価がユーザー数に比例しないこと（`08-ai-architecture.md` §3.4）を再確認する
- [ ] **弁護士に相談する**

## 5. 未成年ユーザーの個人情報

### 5.1 令和8年改正個人情報保護法

令和8年改正個人情報保護法（令和8年法律第56号、**2026年7月17日公布**）は、
**16歳**を閾値として、こどもの個人情報について利用目的の通知・一定の同意取得の相手方を
**法定代理人**とする規律を新設し、16歳未満本人からの利用停止・第三者提供停止請求も
要件を緩和して認めるとされる。

> ※ こども規律の**具体的な施行日は政令待ち**で **要検証**。罰則の一部は公布後6か月、
> 本体は公布後2年以内に政令で定める日に施行とされる。

想定ユーザーは高校生であり、高1には16歳未満が確実に含まれる。
さらに**弱点データ（どの分野を何回間違えたか）は成績プロファイル**であり、
その一部を AI プロバイダへ送信する設計になっている。

### 5.2 MVP の時点で入れる（後付け不可）

**`users` テーブルに次を最初から持たせる。** 後付けすると施行後に全ユーザーへ再同意を取り直す必要が生じ、
同意が取れないユーザーのデータは削除するしかない（＝弱点DBの学習資産が消える）。

```sql
CREATE TABLE app_user (
  id                    uuid PRIMARY KEY,          -- auth.users.id を参照
  display_name          text,
  birth_date            date NOT NULL,             -- ★ サインアップで必須取得
  guardian_email        text,                      -- 16歳未満のとき必須
  guardian_consent_at   timestamptz,               -- 16歳未満のとき必須
  consent_version       text NOT NULL,             -- 同意した規約のバージョン
  consent_at            timestamptz NOT NULL,
  invited_by            uuid REFERENCES app_user(id),
  daily_generation_quota smallint NOT NULL DEFAULT 10,   -- 1日に生成できる教材ユニット数
  created_at            timestamptz NOT NULL DEFAULT now(),
  CHECK (
    birth_date > (CURRENT_DATE - INTERVAL '16 years')
      IS NOT TRUE                                   -- 16歳以上
    OR (guardian_email IS NOT NULL AND guardian_consent_at IS NOT NULL)
  )
);
```

### 5.3 サインアップのフロー — **16歳未満は受け付けない**（作者判断・2026-09-02）

**当初の仕様は保護者の同意を取る流れだった。作者の判断で「受け付けない」に変えた。**
下に旧仕様を残してあるのは、なぜ変えたかを後から辿れるようにするためである。

```
1. 招待コードを入力（invite_code。作者が発行、上限10名 = §3.2 G1・G7）
2. Google ログイン ／ メールリンク（docs/03 §7）
3. 生年月日を入力（必須）
   16歳以上 → 本人同意（規約・プライバシーポリシー）→ 完了
   16歳未満 → **断る。アカウントを作らない**
```

**旧仕様（採らなかった）**

```
   16歳未満 → 保護者のメールアドレスを入力
             → 保護者宛に確認メールを送信
             → 保護者がリンクを踏んで同意 → guardian_consent_at を記録 → 完了
```

**なぜ変えたか**

| | 理由 |
|---|---|
| 依存が減る | 保護者へメールを送る経路（送信サービスと、その鍵）が要らなくなる。**秘密を1つ増やさずに済む** |
| 規律に入らない側に倒れる | §5.1 の16歳未満の規律に、そもそも該当する利用者がいなくなる。政令待ちで施行日が未確定（要検証）な規律に、実装を賭けずに済む |
| 公開範囲と釣り合う | 上限10名の招待制（G7）である。保護者同意のためだけの経路を1本引く投資に見合わない |

**代償**

- **高1（15〜16歳）の友人を招待できない。** 作者はこれを承知の上で選んだ
- 生年月日は**自己申告であり検証できない**。16歳未満が16歳以上と偽って登録することは
  技術的に止められない（`14-open-questions.md` の残存リスクとして記録）。
  できるのは「申告どおりなら断る」までである

**スキーマは変えない。** `app_user.guardian_consent_required` / `guardian_email` /
`guardian_consent_at` は残す。実装は常に `guardian_consent_required = false` を入れる
（16歳未満が入らないため）。列を落とすと、後から16歳未満を受け入れる方針に戻したときに
`5.2` の「後付け不可」の問題が再び立つ。**列を残す費用はゼロで、消す費用は再同意である。**

**実装**: `lib/auth/age.ts`（`MIN_AGE = 16`・満年齢の判定）／
`lib/auth/signup.ts`（DB に触る前に年齢で弾く）／`app/(auth)/profile/`（入力画面）

### 5.4 削除請求への対応

16歳未満から利用停止請求が来たときに、**弱点DB・集中特訓・確認テスト結果を横断削除する導線**が
無ければ法定期間内に対応できない。

- 全テーブルに `user_id` の外部キーを張り、`ON DELETE CASCADE` を設定する
- **論理削除ではなく物理削除できる設計**にする
- アプリ内に「アカウントとすべての学習データを削除する」ボタンを置く
- 削除の実行結果（削除件数）をユーザーに表示する

### 5.5 プライバシーポリシーに明記すること

- 学習履歴（どの問題をいつ、どう間違えたか）を保存すること
- **どの単元・どの項目が苦手かの識別子を Google（Gemini API）へ送信する**こと（§8b）。
  氏名・メールアドレス・生年月日・解答履歴そのものは送信しないこと
- YouTube 動画を再生すると **Google に情報が送信される**こと（`09b-video.md` §5.5）
- 保存期間と削除方法
- 削除申立て・問い合わせの窓口

## 6. 模試・確認テスト画像の取り込み（Phase2）

v0.1 は「**模試の画像を添付するだけで弱点データベースに保存される**」を将来機能としていた。

**模試（河合塾・駿台・ベネッセ・東進等）の問題は民間企業の著作物であり、大学入試ではないため
36条の議論の余地すらない。** ユーザーが撮影・アップロードする行為はユーザーによる複製だが、
サーバに保存し、AI で解析し、解析結果をアプリの機能として提供する事業者は、
**カラオケ法理・ロクラクII 判決以降の枠組みで侵害の主体と評価されうる**。

### 6.1 決定（MVP のスキーマに反映済み）

| # | 決定 |
|---|---|
| L1 | **原本画像を保存しない。** 抽出後すみやかに破棄する（`evidence_import.purge_after` 既定30日以内、実運用は抽出直後） |
| L2 | 残すのは抽出済みの**構造化 claim のみ**（`evidence_claim`） |
| L3 | 「AIが参照できる過去問データベース」に模試を**取り込まない** |
| L4 | 削除申立ての窓口と対応手順を用意する |

**原本を貯める設計のままリリースすると、後から権利処理のためにストレージ全消しと
スキーマ変更が必要になる。**貯めた画像を後で消しても、貯めていた事実は消えない。

> ※ 情報流通プラットフォーム対処法（旧プロバイダ責任制限法）は2024年5月17日公布・
> 2025年4月1日施行で、削除申告への対応迅速化と運用の透明化を規定する。
> 大規模事業者向けの義務であり個人開発アプリが指定を受けることはないが、
> 送信防止措置を講じない場合の民事責任は別途残る。

## 7. Wikipedia と CC BY-SA 4.0

外部リンクを張るだけなら著作権法上ほぼ問題ない（リンクは複製でも公衆送信でもない）。

問題は **AI生成教材**である。日本語版 Wikipedia は CC BY-SA 4.0 であり、翻案物には
(1) 適切なクレジット表示 (2) ライセンスへのリンク (3) 変更した旨の表示
(4) **同一または互換ライセンスでの頒布（継承）** が義務づけられる。

**典型的な破綻パターン**: 利用規約に「本サービス上のコンテンツの著作権はすべて運営者に帰属し、
複製・再配布を禁じる」と書くこと。これは CC BY-SA 4.0 の継承条件に真っ向から違反する。

### 7.1 決定

**教材生成のコンテキストに Wikipedia 本文を一切渡さない**（`07-content-pipeline.md` §11）。
モデルの事前学習知識のみを使い、`material.source = 'ai_generated_no_external_text'` を記録する。

MVP では教材にリンクを張らないため（`07` §10）、Wikipedia との接点は存在しない。
Phase2 で自前 Wiki を作る場合は、この決定を再検討する必要がある。

## 7b. 歴史的国境データ（historical-basemaps）と GPL-3.0（2026-09-05 追加・作者の確認待ち）

「調べる」の版図の再生（`11` §4.1）は、境界線に **historical-basemaps**（André Ourednik、
https://github.com/aourednik/historical-basemaps）の GeoJSON を使う。上流のリポジトリのライセンスは
**GPL-3.0** で、README にデータだけ別のライセンスとする記載は無い。したがって、そこから作った
`lib/map/territory-geo/*.ts`（ビルド時に投影して焼いたパス文字列）は **GPL-3.0 の派生物として扱う**。

| 義務 | 対処 |
|---|---|
| ライセンス本文の同梱 | `lib/map/territory-geo/LICENSE` に上流の写し。生成物のヘッダにも明記 |
| 出典表示 | 版図の図の脚注に作者名・データ名・ライセンス・「加工後も GPL-3.0 で再配布」を出す。取得元のコミットを固定して記録 |
| 対応するソースの提供 | 生成スクリプト（`scripts/map/fetch-historical.mjs` / `build-territories.mjs`）と固定コミットで再現できる。利用者に求められたら生成物とスクリプトを渡せる状態を保つ |
| 継承（コピーレフト）の範囲 | 境界データは**国家ごとの別 chunk**に隔離し、アプリ本体と同じファイルに混ぜない。ただし「アプリと一緒に配信する派生データ」に GPL の継承がどこまで及ぶかは確立していない。HISTORIA 本体にはライセンス表示が無い（既定で全権利留保）ため、**本体のライセンス方針を決めるまでは試作の範囲に留める** |

Natural Earth（基図）はパブリックドメインで、この節の対象ではない。

### 7b.1 作者が確認すること
- 上流の作者にデータの意図するライセンス（GPL-3.0 か CC 系か）を問い合わせる。CC BY 系なら §7 と同じ扱いになる
- HISTORIA 本体をどのライセンスで公開するか（招待制でも配信は「conveying」に当たる）
- 確認が取れるまで、境界データを使う国家は増やさない（試作はオスマン帝国の 3 段階のみ）

## 8. AI 生成教材の来歴と権利帰属

歴史的事実そのものは著作物ではないが、「**どの事実をどう選び、どう配列し、どう表現するか**」は
保護されうる。生成教材が既存教材（山川出版社の教科書・用語集、参考書）の表現に依拠・類似した場合の
翻案権侵害リスクへの手当てが必要である。

**クレームが来た際に「この教材はどのモデルに、どのプロンプトで、いつ生成したものか」を証明できなければ、
依拠性の否認ができない。**

```sql
-- material テーブル（03-data-model.md）に最初から持たせる
model          text NOT NULL,
prompt_version text NOT NULL,
source         text NOT NULL DEFAULT 'ai_generated_no_external_text',
generated_at   timestamptz NOT NULL,
human_edit_log jsonb NOT NULL DEFAULT '[]'::jsonb   -- 人手編集の履歴
```

数万件生成した後では遡及付与できないため、**最初から記録する**。

なお、AI生成物は人間の創作的寄与が乏しければ著作物として保護されず、
運営者は自作コンテンツとして独占できない。「教材の著作権は運営に帰属」と規約に書いても
AI生成部分については実効性が乏しい。対抗するには**人間による編集・監修の痕跡がログとして必要**であり、
`human_edit_log` はそのために置く。

## 8b. AI にデータを送ることの扱い（v0.3 で追加 / 2026-09-04 改訂）

作者の指示により、AI は**二層構成**とする（`08-ai-architecture.md` §2）。

| | 送信先 | 枠 | 送る内容 |
|---|---|---|---|
| **生成** | **Anthropic（Claude Opus 5）** | **課金** | KC の id・3段階の習得度・単元id |
| **検証** | **Google（Gemini 3 Pro）** | **課金** | 教材から抽出した歴史的記述のテキストのみ |

★ **2026-09-04 に2社が入れ替わり、無料枠が無くなった。**
2026-09-02 の実測でこの鍵から無料枠の存在を確認できず（`14-open-questions.md` M28）、
「生成は0円」という前提が崩れたためである（`08-ai-architecture.md` §2 の注記）。

**この改訂で、本節が扱っていたリスクの中心が消えた。**
以前は「学習履歴の識別子を運ぶ生成プロンプトが、唯一の**無料枠**経路である」ことが
問題だった。いまはその重いほうが有料枠に移り、軽いほう（個人情報ゼロの検証）だけが
Google へ行く。**リスクは小さくなっており、大きくなってはいない。**

★ **それでも §8b.1 の匿名化はやめない。**理由は2つ。
(1) 有料枠でも「送っていない情報は漏れない」という保証だけは規約に依存しない。
(2) 退避計画（`08-ai-architecture.md` §3.5）で無料枠に戻る可能性が残っている。
**規約が変わっても壊れない対処を、設計の側に持っておく。**

★ **「有料枠なので学習に使われない」を既成事実として書かない。**
両社ともそう案内しているが、規約は変わる。§8b.2 の文言と R9 は、
**確認した日付とともに**書くこと。

### 8b.1 決定: 個人識別情報を一切送らない

教材生成に必要なのは「**どの KC が弱いか**」であって「**誰が**」ではない。

| 送ってよい | 送ってはいけない |
|---|---|
| `syllabus_unit.id`（公開されている教科書の章立て） | `user_id` / 表示名 / メールアドレス |
| `kc.id`（本アプリが定義した公開語彙） | **生年月日**（16歳未満の判定に使う情報） |
| 習得度の帯（`low` / `mid` / `high` の3段階） | 生の正答率・解答時刻・解答履歴 |
| 反復して選ばれた誤選択肢のラベル（歴史用語） | 連続学習日数・累計解答数などの行動ログ |
| 範囲指定の自然文（ユーザーが自分で書いた短文） | それ以外の自由入力 |

送信内容は「イスラーム史のこの3項目が弱い学習者向けに教材を書け」という形になり、
**特定の個人に紐づかない**。

実装では型で強制する（`08-ai-architecture.md` §4.2）。
`AnonymizedContext` を通らないコンテキストを LLM クライアントに渡せないようにし、
個人識別情報が混入しないことをテストで固定する。

### 8b.2 プライバシーポリシーに書く文言

**送信先が2社になるので、両方を明記する。**

★ **2026-09-04 に2社の役割が入れ替わった。**（`08-ai-architecture.md` §2.3）
生成が Google →**Anthropic**、検証が Anthropic →**Google**。社名は同じでも、
**どちらに学習履歴が行くかが変わる**ので、文言をそのまま流用してはいけない。

> **学習内容の生成のため**、あなたが苦手としている単元・項目の識別子を Anthropic（Claude API）へ送信します。
> 氏名・メールアドレス・生年月日・解答履歴そのものは送信しません。
>
> **生成された文章の事実確認のため**、教材から抽出した歴史的な記述
> （「◯◯条約は△△年に締結された」等）を Google（Gemini API）へ送信します。
> **この送信にあなたに関する情報は一切含まれません。**
>
> いずれも有料の枠を利用しています。

★ **「学習に使われません」と書く前に、両社の現在の規約を読むこと。**
以前の文言は「無料枠なので Google のサービス改善に利用される場合があります」と
**利用される側に倒して**書いてあり、正直だった。有料枠に移ったことで
「使われない」と書きたくなるが、**それは規約を読んで確かめてからでないと書けない**。
ここは法的な表明であり、実装の都合で書き換えてよい場所ではない。
確かめるまでは、上のとおり枠だけを述べて学習の可否には触れない。

**この文言を正直に書けない設計にしない。** 書けるように §8b.1 と §8b.4 を守る。

### 8b.4 検証側は個人情報を含まない

検証プロンプトに渡すのは、教材本文から抽出した `claims`（歴史的主張の配列）だけである。

```
送る:      「アッバース朝は750年に成立した」というテキスト
送らない:  user_id / KC の id / 習得度 / 単元id / その他一切
```

**KC の id すら渡さない。** 検証に必要なのは主張そのものだけであり、
誰の教材から出た主張かは判定に関係しない。
したがって検証側には匿名化処理すら不要である（渡す情報に個人が存在しない）。

実装上は、生成側の `AnonymizedContext` とは別に `Claim[]` 型を定義し、
**検証クライアントは `Claim[]` しか受け取れないようにする**（`08-ai-architecture.md` §6）。

### 8b.3 残るリスク

| # | リスク | 状態 |
|---|---|---|
| 1 | 範囲指定の自然文にユーザーが個人情報を書き込む | 入力欄に注意書きを出す。100字上限にする |
| 2 | 「どの項目が弱いか」の組み合わせが十分に特異なら準識別子になりうる | 利用者が数人のため理論的なリスク。**要検討** |
| 3 | 規約が変わる | 規約を定期的に確認する。**2026-09-04 に無料枠をやめて両方を課金枠にした**ので、「無料枠の規約変更」という形では起きなくなった。プロバイダを替えるなら `08-ai-architecture.md` §6 の抽象層で切り替える |

## 9. AI プロバイダの未成年向け要件

Anthropic は、未成年にサービスを提供する組織に対して次を求めている
（詳細は `08-ai-architecture.md` §7）。

- 年齢確認
- コンテンツモデレーション・フィルタリング
- 監視・報告体制
- 児童プライバシー法の遵守
- 提供される子ども向けシステムプロンプトの実装

**これは規約上の提供条件であり、違反によるアカウント停止はサービスの即死を意味する。**

| 要件 | 本アプリでの実装 |
|---|---|
| 年齢確認 | 生年月日の必須取得（§5.2）＋16歳未満は保護者同意（§5.3） |
| モデレーション | **v0.3 で人手レビューが不可能になった**（毎回生成）。機械照合＋**別系統モデルによる二次照合**＋FLAG段落の非表示で代替する（`08` §5）。ユーザーの自由入力は範囲指定の短文のみ |
| 監視・報告体制 | `content_report`（`08` §5 層4）＋削除申立て窓口（§3.2 G6） |
| 子ども向けシステムプロンプト | `07-content-pipeline.md` §5.1 に組み込む |
